# Autentificare JWT: plan de implementare

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** register / login / refresh rotativ cu detectarea reutilizării / logout / me pe backend-ul .NET 8, cu refresh token în cookie HttpOnly și access token JWT de 15 minute.

**Architecture:** Clean Architecture existentă. Regulile tokenului și ale blocării contului stau în Domain. Cazurile de utilizare sunt comenzi MediatR în Application, care depind doar de interfețe (`IPasswordHasher`, `ITokenService`, `IDateTimeProvider`). Implementările criptografice stau în Infrastructure. WebApi se ocupă doar de HTTP (cookie, ProblemDetails, rate limit, CORS).

**Tech Stack:** .NET 8, EF Core 8 + Npgsql, MediatR 14, FluentValidation 12, `Microsoft.Extensions.Identity.Core` (PasswordHasher), `Microsoft.IdentityModel.JsonWebTokens`, xUnit + FluentAssertions + Moq, EF Core InMemory, `Microsoft.AspNetCore.Mvc.Testing`, `Testcontainers.PostgreSql`.

**Spec:** `aplicatie/docs/specs/2026-10-16-auth-jwt-design.md`. Citește-l înaintea oricărui task; secțiunile sunt referite ca §N.

## Global Constraints

- Toate comenzile `dotnet` rulează din `aplicatie/backend/`. Commit-urile se fac pe branch-ul `feature/NUT-auth-jwt`.
- Cod, comentarii, nume de tabele și mesaje de commit: **engleză**, cu *Conventional Commits* (`feat:`, `fix:`, `test:`, `docs:`, `sec:`, `refactor:`). Mesajele afișate utilizatorului (titluri ProblemDetails): **română**, exact cum le dă §4.
- Fiecare mesaj de commit se încheie cu linia `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Teste: Arrange-Act-Assert, cu comentarii `// Arrange`, `// Act`, `// Assert`; numire `Method_Scenario_ExpectedResult`; FluentAssertions.
- Valori fixe: access token **15 min**; refresh token **7 zile**; refresh token = **32 de octeți** aleatori, Base64Url; hash refresh = **SHA-256 hex, cu litere mici, 64 de caractere**; PBKDF2 **210.000** iterații; blocare după **5** eșecuri, timp de **5 min**; parolă **8–128** caractere; email maximum **256**; nume maximum **100**; rate limit **10 cereri / 60 s / IP**; `ClockSkew` **30 s**; secret JWT minimum **32 de octeți**.
- Cookie: nume `nutriscan_rt`, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/auth`, `Max-Age` 7 zile.
- Timpul curent se obține **numai** prin `IDateTimeProvider` în Application. Nu se folosește `DateTime.UtcNow` în handlere.
- Nu folosi `ExecuteUpdateAsync` / `ExecuteDeleteAsync`: providerul InMemory din testele unitare nu le suportă.
- Parolele, tokenurile și hash-urile nu se loghează niciodată.
- Toate pachetele `Microsoft.IdentityModel.*` trebuie să ajungă la aceeași versiune. Verificare: `dotnet list package --include-transitive | grep IdentityModel`.
- Fișierul `documentatie/pregatire_sustinere/intrebari_comisie.md` nu se adaugă niciodată în git.

## Review Focus

1. **Email cu majuscule sau spații la login** (`"  Ana@X.ro "` după înregistrarea cu `ana@x.ro`). Utilizatorul se așteaptă să intre. Testul `Handle_EmailWithDifferentCaseAndSpaces_LogsIn` e în Task 5.
2. **Refresh după ce utilizatorul a fost șters.** Tokenul are cascade delete, deci dispare odată cu utilizatorul; ne așteptăm la 401, nu la 500. Testul `Handle_TokenNotFound_ThrowsUnauthorized` e în Task 6.
3. **Logout cu cookie expirat sau inexistent în DB.** Răspunsul trebuie să fie tot 204, nu eroare. Testul `Logout_WithUnknownCookie_Returns204AndClearsCookie` e în Task 9.
4. **Cookie-ul trebuie șters și la 401 de pe `/refresh`.** Middleware-ul de excepții golește header-ele răspunsului, deci ștergerea trebuie făcută în controller. Testul `Refresh_WithReusedToken_Returns401AndClearsCookie` e în Task 9.
5. **Corp JSON lipsă sau `null` la register/login.** Răspunsul trebuie să fie 400 ProblemDetails, nu 500. Testul `Register_WithEmptyBody_Returns400` e în Task 8.
